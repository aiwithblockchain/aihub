# TweetClaw 二期需求文档

## 需求 1：小红书笔记评论的回复（二级评论 / 楼中楼）API

### 背景
当前 TweetClaw 的小红书（Xiaohongshu）数据采集模块已经支持获取笔记的一级评论（即用户对笔记的直接评论），但尚不支持获取**评论的回复**（又称二级评论、楼中楼）。即：用户 A 对某条笔记发表评论后，用户 B 对该评论进行了回复，目前系统无法抓取这部分数据。

### 需求描述
新增 API（或扩展现有评论 API），使其能够获取指定一级评论下的所有回复内容。

### 目标平台
- 小红书（Xiaohongshu / RED）

### 数据范围
- 输入：某条笔记下的一级评论 ID（或评论对象）
- 输出：该评论下的所有二级评论（回复）列表，包括但不限于：
  - 回复内容（文本）
  - 回复者信息（用户 ID、昵称、头像等）
  - 被回复者信息（若为回复给特定用户）
  - 回复时间
  - 点赞数
  - 回复 ID（用于后续可能的翻页或追踪）

### 技术考量
- 小红书 App 或 Web 端对评论回复通常采用分页（分页加载或游标分页），需实现翻页逻辑以获取完整回复列表。
- 需评估反爬策略：频繁请求评论回复接口可能触发风控，需考虑请求频率控制、代理轮换、登录态维护等。
- 数据结构建议与现有的一级评论模型保持一致或兼容，便于下游统一处理。

### 优先级
高

### 验收标准
1. 传入有效的一级评论 ID，能够成功返回该评论下的所有二级评论（支持翻页获取全部）。
2. 返回字段至少包含：回复内容、回复者昵称/ID、被回复者昵称/ID（如有）、点赞数、发布时间。
3. 若该评论无回复，返回空列表而非报错。
4. 异常情况（评论不存在、被删除、接口限流）需有明确的错误码和提示信息。

## 需求 2：各平台内容 @提及（Mentions）获取 API

### 背景
当前 TweetClaw 的互动消息获取工具仅支持**直接评论**（comment），不支持获取对内容的 **@提及/标签提及**（mentions）。这类数据对于用户互动分析和运营反馈至关重要。

### 需求描述
新增或扩展现有互动消息获取 API，使其能够获取指定内容被提及的情况（包括但不限于：被转发并@、被引用并@、被评论中@等）。

### 目标平台
- X（Twitter）
- Xiaohongshu（小红书）
- Instagram（IG）

### 数据范围
- 输入：指定内容 ID（推文/笔记/媒体 ID）
- 输出：包含该内容或账户的所有提及列表，包括但不限于：
  - 提及类型（转发+评论、引用、直接提及等）
  - 提及来源内容 ID 及 URL
  - 提及者信息（用户 ID、用户名/昵称等）
  - 提及时间
  - 提及内容摘要（含完整文本或截断文本）
  - 原始提及对象（如被@的目标用户/内容）

### 技术考量
- **X（Twitter）**：
  - Twitter API 2.0 的 `search/recent_tweets` + 搜索过滤器可获取提及，需评估 Tweet 级权限
  - 部分提及数据仅通过付费 API 或企业级权限可用
  
- **Xiaohongshu（小红书）**：
  - 小红书仅支持系统通知中的 @提及数据，无独立的"获取某笔记的所有提及"API
  - 需通过 `get_notifications_raw` 等通知接口获取
  
- **Instagram（IG）**：
  - Instagram Graph API 中的 mentions 需要 `instagram_graph_user_profile` 权限
  - 可能需要额外的登录态和权限管理

### 优先级
中-低（相对于直接评论的重要性）

### 验收标准
1. 对于支持 mentions 的平台（X、IG），能够返回该内容被提及的列表
2. 返回字段至少包含：提及者、提及时间、提及文本摘要、原始提及来源 URL
3. 若内容无提及记录，返回空列表
4. 异常情况（权限不足、内容不存在等）需有明确的错误提示
5. XHS 提及通过通知系统集成，与其他平台返回格式保持一致

## 需求 3：Go LocalBridge 超时时间可配置化

### 背景
当前 Go LocalBridge 桥接层的 REST API Handler 中，各端点的 WebSocket 转发超时时间均为硬编码（例如 `igPostMedia` 固定为 60 秒、默认端点为 30 秒）。实际业务中，某些平台操作（如 Instagram 多图轮播上传、视频发布）因包含多次图片上传、智能延迟和 API 调用，耗时可能超过 60 秒，导致 Python 客户端收到 `504 Gateway Timeout` 错误，而扩展端实际已成功完成操作。

目前 Python 层的 `requests` 超时可通过参数调整，但 Go 桥接层作为 WebSocket 转发代理，其内部 `time.After(timeoutMs)` 才是 504 的真正来源，Python 侧的超时设置无法覆盖它。

### 目标平台
- Go LocalBridge（`localBridge/go-lib/pkg/restapi/handler.go`）

### 需求描述
将 Go LocalBridge 中的端点超时时间从硬编码改为可通过配置注入，使入口层（`main.go`）加载的配置能够向下透传并影响 Handler 行为。

### 技术考量
- **配置链路现状**：
  - `config.Load()` 已加载 `~/.config/localbridge/config.json`，但 Config 结构体目前仅包含 WebSocket/REST 的 `Addresses` 字段。
  - `bridge.go` 接收 `cfg` 后仅提取地址列表，未将 `cfg` 本身透传给 `restapi.NewServerWithRegistrar()`。
  - `server.go` 创建 `Handler` 时只传入 `ws`，未传入任何配置或超时值。
  - 因此 `handler.go` 中的超时只能硬编码，无法从外部配置。

- **建议方案**：
  1. **Config 扩展**：在 `config.Config`（或 `ServiceConfig`）中增加超时相关字段，例如 `DefaultTimeoutMs` 或按业务模块划分的超时配置。
  2. **桥接层透传**：修改 `bridge.NewWithRESTRegistrar()` 和 `restapi.NewServerWithRegistrar()` 的签名，将超时配置（或整个 `cfg` 对象）传递至 RESTAPI 层。
  3. **Handler 改造**：`NewHandler()` 接收超时配置并存入结构体；各端点函数（`igPostMedia`、`igPostVideo` 等）引用该配置值，替代现有的硬编码字面量。
  4. **向后兼容**：若配置文件中未指定超时，则使用与当前硬编码一致的默认值（如媒体发布 180s、普通操作 30s），确保现有部署不受影响。

### 优先级
中

### 验收标准
1. `main.go` 入口点加载的配置能够影响 `handler.go` 中端点的超时行为。
2. `igPostMedia`、`igPostVideo` 等长耗时端点的超时时间不再以字面量形式写死在 Handler 中。
3. 配置文件未指定超时时，系统行为与当前硬编码值完全一致，保证向后兼容。
4. 重新编译并启动 LocalBridge 后，Python 客户端的多图/视频发布不再因 Go 层 60s 超时触发 504（前提是实际业务耗时在配置允许范围内）。
